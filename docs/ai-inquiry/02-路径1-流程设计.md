# 路径 1（纯表单）· 流程设计与优化

> 范围：`/quote` 公开版客户流程（`/quote/internal` 暂不动）。
> 目标不是「加功能」，而是**把客户不需要做的决定从流程里拿走**，让 3 步变 2 步，让数字只有一个出口。
> 本文是设计稿，等决策点（§8）确认后再动手。

---

## 一、现状流程的六个结构性问题

| # | 问题 | 证据 |
|---|---|---|
| P1 | **因果倒置**：第 3 步选「整车/拼货」，决定第 2 步体积是否必填 | `useQuoteForm.ts:215-218` 拼货缺体积 → 第 2 步不放行；客户填完货才知道要回补体积 |
| P2 | **让客户做他不该做的决定**：选车型、选整车/拼货、5 个绕行开关 | `VehicleStep.tsx:56-177`；开关文案是「空返/限行区/施工绕行/山路附加」，全是我方内部计费口径 |
| P3 | **第 1 步信息过载**：起终点各 1 个搜索框 + **各 2 个经纬度输入** + 可无限加的途经点（每个又是 1 框 + 2 坐标）+ 一张常驻地图 | `RouteStep.tsx:57-205` |
| P4 | **第 2 步最坏 7 字段/行**：名称/件数/长/宽/高/单件重量/可堆叠 × N 行，默认 `count=1, lengthM=0` | `CargoStep.tsx:170-244` |
| P5 | **结果只有一个出口，且没有下一步动作**：只有页面内 `q-results`，客户算完只能自己抄或跳 `/contact`（不带方案） | `QuoteApp.tsx:439-466`、`PublicResult.tsx:62` |
| P6 | **服务端其实已能自动配车，前端却不让提交** | `quoteProxy.ts` `normalizeRequest()`：`full_truck` 缺车型时按载重升序自动匹配；但 `canNext(2)` 要求 `vehicleModelId` 必填 → 这条能力客户永远用不到 |

> P6 是关键：**「系统推荐车型」不是新功能，是已有能力被前端锁住了**。

## 二、优化后的流程（公开版）

### 从 3 步变 2 步

步骤去掉「车型」这一独立步骤，车型并入第 2 步（预选推荐）。骨架见下方「视觉骨架（决策后）」。

### 三处结构性改变

1. **车型：默认预选系统推荐值，客户可改（不再是从零选择）**
   第 2 步里填完重量 → 车型区显示「系统推荐：高栏 13 米 · 26 t ✅ 已选」，点开可换
   推荐链路：`fit-vehicles`（有单件尺寸走四约束，没尺寸按载重合车）→ 预选 → 再 `route/cost`
   **车型仍是必选项**（引擎 `full_truck` 硬要求 `vehicle_model_id`），但客户不需要「从 12 个车型里挑一个」。

2. **只保留整车模式**（2026-11-22 定）：`loadingMode` 固定 `full_truck`，拼货（consolidated）分支下线
   连带影响：**体积不再是必填**（拼货才需要体积）→ 体积变可选，不填不影响提交
   收益：P1（因果倒置）整条消失，客户少一个看不懂的选择；`canNext(1)` 永不为体积拦人

3. **高级选项收进折叠**：坐标、途经点、地图、货值、开关。默认全部不出现。
   经纬度和「山路附加费」是操作员语言，不是客户语言。

### 视觉骨架（决策后）

```
┌─ 01 路线 ─────────────────────────────────────────┐
│  起运地 [搜索]   目的地 [搜索]   经口岸 [系统推荐 ▾] │
│  ▸ 高级：途经点 / 手填坐标 / 地图选点                 │
└───────────────────────────────────────────────────┘
┌─ 02 货物 ─────────────────────────────────────────┐
│  重量 [    ] 吨⇄公斤    货类 [普通货物 ▾]           │
│  大件/超限 [开关] → 单件明细表（7 字段/行）           │
│  体积 [    ] m³（可选，不填则估算并明示）             │
│  车型  ● 高栏 13 米 · 26 t   ← 系统推荐，已预选       │
│        ▸ 换车型（展开车型库，按类别分组）             │
│  ▸ 高级：货值 / 空返 / 装卸 / 绕行                    │
└───────────────────────────────────────────────────┘
                    ↓ 「测算运费」
┌─ 结果 ────────────────────────────────────────────┐
│  车数 2 辆 · 高栏 13 米 · 26 t（引擎按尺寸核过）      │
│  里程 386 km · 约 5.7 h（含装卸/休息）               │
│  参考运费 15,900,000 – 19,400,000 VND               │
│  动作：换车型重算 / 改信息 / 复制 / 提交正式询价      │
└───────────────────────────────────────────────────┘
```

### 字段总账（公开版）

| 字段 | 现状 | 优化后 | 理由 |
|---|---|---|---|
| 起运地 / 目的地 | 搜索框 + 2 个坐标框 | 搜索框（坐标进高级） | 坐标对客户是噪音 |
| 经口岸 | 只能靠途经点 | 显式下拉，默认系统推荐 | 客户真正关心「走哪个口岸」，现在没有入口 |
| 途经点 | 常驻可加 | 高级里 | 少数场景 |
| 地图 | 常驻整块 | 高级里，点开才加载 | 首屏空间与懒加载 |
| 重量 | 必填 | 必填（不变） | 计价核心 |
| 体积 | 拼货必填、整车可选 | **永远可选**（拼货下线后没有必填场景） | 解 P1：没有倒灌 |
| 货类 | 必选下拉 | 默认「普通货物」 | 减少一次点击 |
| 货值 VND | 主流程可见 | 高级里 | 客户不知道且币种别扭 |
| 单件明细 | 常驻表（7 字段/行） | 「大件/超限」开关后才出 | 只有大件需要 |
| 整车/拼货 | 必选 | **整条下线**，固定整车（2026-11-22 定） | 解 P2/P1 |
| 车型 | 必选（按 5 类分组的长列表） | 必选但**已预选推荐值**，可展开换 | 解 P2：不用从零挑 |
| 5 个开关 | 常驻 5 个 | 高级里 | 内部计费口径 |
| 成本参数 | 第 4 步（内部版） | 不变 | 内部版不动 |

**净效果**：公开版客户从「最多 20+ 个控件」降到**首屏 3 个必填 + 2 个可选**。

## 三、性能与调用时序（避免 P6 那种重复计算）

```
点「测算运费」
  ① POST /api/quote/fit-vehicles   ← 新增公开代理（透传 server/tools/fleet.ts）
       入参：weight_kg + volume_m3? + cargo_type + items?（无尺寸则合成一行）
       出参：groups[{model, category, vehicle_count, reason, flags}] + oversize
  ② 取 ① 的首组车型 → POST /api/quote/route（full_truck + vehicle_model_id）
  ③ 渲染结果
```

- ①失败（引擎不可用/超限配不上车）→ 结果页显示「需人工评估」+ 提交询价，**不静默退回按载重猜**。
- ①②都在服务端串行，浏览器只打本站（`CONTRACT §3` 不变）。
- 缓存：①的结果与 `reference` 一起按「路线+货物指纹」记忆 30 秒，客户来回改开关不重复打引擎。

## 四、留资与线索（解 P5）

结果页「提交正式询价」→ 弹留资（复用站内 `src/tools/LeadModal.tsx` + `POST /api/lead`），并附带方案快照：

```json
{ "source": "quote", "route": {...}, "cargo": {...}, "vehicle": {...},
  "result": { "km": 386.8, "hours": 5.7, "vehicle_count": 1, "price_range": [15900000, 19400000] } }
```

> 现状 `/quote` 完全没接留资（已 grep 确认）。这是「算完就走」的直接原因。
