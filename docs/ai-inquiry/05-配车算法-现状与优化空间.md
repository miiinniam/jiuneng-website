## 二、现有能力清单（引擎已实现，可直接用）

| 能力 | 代码位置 | 说明 |
|---|---|---|
| 四约束车数 | `费用计算公式.车辆数分解()` | 重量 / 体积 / 单件最长 / 总占地，各算一遍取 max，并给出**主因** |
| 单件超载不可分 | 同上（`不可分` 键） | 单件 > 该车核定载重 ⇒ 该车型不可用，多派车也解决不了 |
| 货行分档 | `line_tier()` | 档0 超重件（>32t）/ 档1 超限件 / 档2 常规件；**决定谁先挑车** |
| 单件可同车上限 | `pieces_per_truck_cap()` | 档2 = min(载重商, 沿车长串联 × 并排 × 叠层) 的**网格算法** |
| 尺寸五档判定 | `width_tier / height_flags / length_flags` | 宽 2.5/3.0/3.5/3.75/4.5/5.5；总高（台面+货高+垫木 0.12）；组合长（货长+前后悬+主车） |
| 轴荷 / 桥涵 | `axle_lines_required()`、`_axle_info()` | 8t/轴线；不足给 `axle_shortfall` |
| 超限开关 | `allow_oversized` | 4.5–5.5m 宽 / 4.75–5.5m 总高可配车+许可标；**超载一字不放** |
| 共车组合 | `COLOAD_POLICY`、`co_load_allowed()`、`pairs[]` | 同车是否成立（CO-1…CO-6），可 `accepted_pairs` 采纳 |
| **逐行锁定车型** | `locked_models: {line_id: model_id}` | **「客户/项目经理指定某行走哪个车」的现成接口** |
| 距离感知选型 | `_rank_key()` + `cost_caliber(distance_km)` | 有距离才比总价；没距离退化 `rate_only` 并**显式标注** |
| 配不出真因 7 类 | `UNFIT_REASONS` E1–E7 | 每条给「最低成本第一步」的处置建议 |
| 折叠策略 | `line_folder` + `fold_shape` | 分瓣/分段（如塔筒、座环） |
| 车数三重口径 | `count_doctrine` | `floor`（件守恒）/ `four_const`（四约束）/ `packer`（**恒为 None**） |

**结论**：客户填「设备尺寸 + 重量 + 件数」，引擎已经能给出「车型 + 车数 + 为什么 + 能不能运 + 要不要许可」。

## 三、四个真缺口（都有代码证据）

### G1 · 官网主流程根本没把设备信息交给算法
- 现状：第 2 步的单件明细是可选输入，第 3 步反而让客户**自己选车型**；`/api/quote/route` 只收总重。
- 后果：`货物载荷特征完整()` 拿不到单件 → 退回 Level 1（只有重量+体积）→ 四约束退化成重量约束 → 车数与车型偏差大。
- 证据：`quoteProxy.normalizeRequest()` 只在缺车型时**按载重升序**挑一个（`fitting = candidates.find(load >= weightTon)`），不传 items 给 fit-vehicles。

### G2 · 不传 `distance_km` ⇒ 选型退化成「费率×车数」
- 引擎注释自己写明：`无距离兜底（设计 §3.1 选择规则②）：前端 fit-vehicles 请求不带距离`，`cost_caliber` 因此恒为 `rate_only`。
- 后果：可能选中「车数少但总价高」的车型（例如 17.5 米 1 辆 vs 13 米 2 辆，只比费率不比总价）。
- **而官网其实拿得到距离**：`/api/quote/route` 先算完就有 `distance_km`。现在三处调用都没利用。

### G3 · `packer`（真实装车模拟）恒为 `None`
- 证据：`count_doctrine: { caliber: "max(floor,4const,packer)", packer: None, gap_warn: None }`，注释写「装车器实测由前端回填」——前端从未回填。
- 后果：车数只取 `max(件守恒下限, 四约束)`，**跨行混装没算**，结果偏保守（多报车）。保守在报价上意味着**报贵了丢单**。
- 影响面：多品种、多规格（如「变压器 + 附件 + 支架」）时最明显。

### G4 · 只输出一套方案
- 引擎支持 `locked_models` 逐行锁定，可以据此枚举「方案 B / C」，但官网没有做组合。
- 后果：客户看不到「全用 13 米 ×2」vs「17.5 米 ×1」的对比，选型不透明。

## 四、优化设计（三层，按性价比排序）

### L1 输入侧（官网，收益最大、成本最低）
把「设备信息」采到位，算法才有数据可算：

| 做法 | 说明 |
|---|---|
| 设备类型模板 | 选「变压器 / 塔筒 / 风机叶片 / 挖掘机 / 成槽机 / 龙门吊 / 集装箱 / 普货」→ 自动带出该类型常见字段顺序与提示 |
| 单件明细默认展开 | 选了设备类就展开（普货才折叠），并给「长 × 宽 × 高 / 件数 / 单重 / 可叠放」的填写示例 |
| 单位引导 | 长宽高强制米（0.1 精度），单重支持吨/kg，与引擎口径一致 |
| 空值兜底 | 只填总重时，UI 明确标「当前按总重估算，车数可能偏大；补充单件尺寸可精算」 |

### L2 调用侧（官网，**本次就能做，不改引擎**）
把调用顺序改成「距离 → 选型 → 报价」：

```
① POST /api/quote/route（先要里程，customer 看不到）
② POST /api/quote/fit-vehicles
     入参带 distance_km（来自 ①）+ items + weight + volume + cargo_type
     出参 groups[]（车型 / 车数 / 主因 / 超限 / 许可）
③ 用 ② 的首选车型（或客户 locked 的车型）再跑 route/cost 出区间
④ 客户在结果页换车型 → 带 locked_models 重跑 ②③
```

- 这一步就修掉 **G2**（选型带距离）和 **G4**（换车型走 locked_models，而不是整车覆盖）。
- 只改 `server/quoteProxy.ts` + 前端编排，**不碰引擎**。

### L3 算法侧（引擎，需另开工作流）
| 缺口 | 方案 | 成本 |
|---|---|---|
| G3 packer | 后端实现轻量一维装箱（沿车长 best-fit + 并排 + 叠层），把 `packer` 从 `None` 变成实数，`caliber` 取 max 才有意义 | 中高（要和 `车辆数分解` 保持同源，`INV-2` 不能破） |
| G1 残余 | 在 `normalizeRequest` 里把 items 直接透传给 fit-vehicles（而不是只在缺车型时按载重猜） | 低 |
| G4 多方案 | 在 `fit-vehicles` 支持「排除某车型后重算」，前端枚举 2–3 个方案 | 低-中 |

> 引擎改动的门禁（项目规矩）：`_vNNN_preflight.py` → pytest（672 条）→ `--pyinstaller` 打包 → 起打包版真机验收。**不能只改源码不打包**。

## 六、验收（算法侧）

| 断言 | 手段 |
|---|---|
| 带 items 与不带 items 的两条路径，车数差可解释 | 同一票货跑两次，断 `/breakdown.主因` 与 `count_doctrine.caliber` |
| 带 `distance_km` 时 `cost_caliber != rate_only` | 读 `count_doctrine.cost_caliber` |
| 设备模板 → 引擎收到的 items 字段完整（无 0 长宽） | 抓 fit-vehicles 请求体 |
| 换车型走 `locked_models`，且总车数与金额按新车型变化 | 对比两次响应 |
| 超限件（宽 4.98m）在 `allow_oversized=false/true` 下两种结局 | 金标准案例（座环 4.98m）回归 |
