# 07 · 官网侧接头勘察与改造计划（只读勘察，未改代码）

> 勘察日期：2026-11-22　│　对象：`JIUNENG 官方网站-源代码` HEAD `f1b16c8` + 引擎 `03_桌面版-AIOSRM++`
> 目的：搞清「客户点进 `/quote` 之后，引擎的配车能力到底有没有被用上」，为流程改造划边界。

---

## 1. 现状：三条链路，互不连通

```
A. /quote 报价工作台（客户/业务用的那条 —— 用户要改的就是它）
   第1步 路线 ─┐
   第2步 货物 ─┼→ quoteRoute() → POST /api/quote/route → quoteProxy → 引擎 POST /quote/route
   第3步 车型 ─┘        ↑                                            （只算钱，不配车）
                车型从 GET /api/quote/reference 的 vehicle_models 列表里**人工挑**

   公开响应（服务端白名单重建）只有：
     distance_km · duration_h · vehicle_count · vehicle{id,name,max_load_ton}
     · price_low_vnd · price_high_vnd · timing · geometry

B. /ai 页工具层（AI 助手用，已能自动配车）
   src/tools/FleetForm → POST /api/fleet-match → 引擎 POST /reference/fit-vehicles
   返回完整 groups：permit_flags · count_doctrine · axle_lines · breakdown · pairs …

C. 引擎（算法唯一真身）
   /reference/fit-vehicles （配车）  ·  /quote/route （计价）
```

**一句话结论**：`/quote` 是「人工选车型 + 引擎算钱」，**自动配车压根没接进来**。
`/ai` 工具层能配车，但那是另一条独立链路，客户在 `/quote` 走不到。

## 2. 缺口清单（按业务影响排序）

| # | 缺口 | 业务后果 | 证据 |
|---|---|---|---|
| **G1** | `/quote` 无自动配车入口 | 客户/业务自己判断车型，选错就报错价 —— 这是最大的错价来源 | `features/quote/src/api.ts` 只有 `fetchReference/geocode/quoteRoute/aiChat/templates/batch/ddp/customs`，无 fit |
| **G2** | 引擎 8 项算法改进在 `/quote` 全不可见 | A1 并排/ A2 装载长度 / A5 叶片车 / A7 一件一车 只惠及 `/ai` 工具层 | 公开响应白名单不含任何配车字段 |

| **G4** | 距离与配车未联动 | 引擎 `fit-vehicles` 支持 `distance_km` 才比总价（否则只按费率排序），`/quote` 有距离却不传 | 引擎 docstring 已写明该参数 |

## 3. 改造计划（4 个切片，按依赖顺序）

### P1｜✅ 已落地（2026-11-22）新增公开端点 `POST /api/quote/fit`

**验收实测（我自己起的引擎 18000 + 站点 3471，非纸面推演）**：`FIT: PASS (12/12)`

| 案例 | 结果 |
|---|---|
| 30 m 塔筒 25 t | 1 车 · 大件抽拉伸缩板 80t/30m · **三类许可 15 工作日** |
| 60 m 叶片 12 t | 1 车 · 风电叶片抽拉车 62m |
| 80 m 叶片 | **0 车**（如实报配不出，无假结果） |
| 1.4 m 钢板 ×2（并排） | 1 车 · 普通平板 13m（A1 并排宽度闸生效） |
| 100 t 轴线车货 | 1 车 · 多轴液压轴线车 100t |
| 13.5 m 设备 35 t | 1 车 · 低平板 17.5m · 许可档位非空（A3 出口） |
| 空 items / 缺 weight_kg | HTTP 400 `bad_request`（**无 500**） |
| distance_km 追加 | 车数与不传时一致（距离不该改配车） |

**泄漏实测**：真实响应逐词扫描 `breakdown / count_doctrine / axle_lines / base_rate / fixed_surcharge / margin / profit / 18000 / secret` → **零命中**。响应只有 8 个白名单字段。

**实现**：`server/quoteProxy.ts` — `buildPublicFit()`(611) + `router.post('/fit')`(838)。三道闸：
1. **入站**逐键重建请求（客户端塞的额外键全丢）；2. **出站**不 spread `group`，只按显式字段新建对象；3. **文案**只从 `permit_flags` 正则抽档位+工作日，`split_hint` 截断 300 字。
排序稳定（车数降序 → model_id 升序），客户刷新不会看到两套方案。

原计划要点（保留）：

- **位置**：`server/quoteProxy.ts` 新增路由（与 `/route` 同层，复用 `callEngine`）
- **入参**（严格白名单，逐项校验类型）：`items[]`（name/length_m/width_m/height_m/weight_kg/count/stackable/divisible）、`cargo_type`、`distance_km`、`allow_oversized`
- **转发**：引擎 `POST /reference/fit-vehicles`
- **出参白名单**（**绝不转发 breakdown / 费率 / 成本**）：
  ```
  { ok, scope:'public', total_trucks, needs_split, split_note,
    picks: [{ model_id, name, max_load_ton, vehicle_count, oversize,
              permit_tier, permit_workdays_local, permit_note }],
    note }
  ```
- **验收**：12 个真案例（含 30 m 塔筒 / 60 m 叶片 / 1.4 m×2 并排 / 100 t 轴线车 / 可解体件）车型与车数逐条等于引擎输出；响应体里 grep 不到 `rate`、`cost`、`margin`、`breakdown`。

### P3｜✅ 已落地（2026-11-22）AI 接配车：车型一律按车型库配置讲

**做了什么**
- `server/tools/vehicleModels.ts`（新）：从引擎 `/reference/vehicle-models` 拉全库 46 款 → `VehicleSpec`（13 个非成本字段）+ 5 分钟缓存 + singleFlight；拉取失败返回空 Map（不抛），`spec` 落 `null` 如实报「库内暂无该参数」
- `server/tools/fleet.ts`：`FleetGroup` 增 `display_name / max_load_ton / spec`，三层回落（库 → 引擎 → model_id）
- `server/agentChat.ts`：`match_vehicles` 工具描述写明「车型名与参数一律取自车辆型号库，禁止自行推断或改写」；工具返回逐键挑 `display_name / max_load_ton / length_m / axle_config`（不塞 spec 整块）；summary 改「库内车型名 · 载 X 吨 · Y 米（轴型） · N 辆」
- **红线**：`VehicleSpec` 类型层面就不留成本字段位（`base_rate / fixed_surcharge / toll_rate / fuel_l_per / notes` 一个都没有）

**验收**：`node --test server/tools/vehicleModels.test.ts` 4/4；`fleet.test.ts` 8/8（含「库说 38 吨、引擎说别的也以库为准」与「成本字段零泄漏 + spec 真挂上」双向断言）；`npx tsc --noEmit` 0。

### P3-B｜✅ 已落地（2026-11-22）`/quote` 报价助手换站内编排，金额只给区间

**为什么必须换**：原 `/ai` 把引擎 SSE 原样透传 —— ① 工具在引擎进程内，我们插不进自己的工具、也下不发表单补丁；② 引擎 prompt 要求输出 13 项运费 breakdown，**客户能在聊天正文看到成本结构**（工作台卡干净 ≠ 页面干净）；③ AI 看不到当前表单。

**做成什么样**
- `server/tools/quoteTools.ts`（新）：7 个工具 `read_form / set_route / set_cargo / set_vehicle / set_conditions / match_vehicles / run_quote`；`quoteSystemPrompt()` 写死「金额只给区间、禁止输出明细/成本项/单价/利润率」
- `server/quoteAi.ts`（新）：站内编排端点（DeepSeek 优先 → Gemini 回退，SSE 单向流）；合规限定语服务端兜底
- `server/agentChat.ts`：`runAgentChat` 开出 `tools / execute / label / system` 可注入参数（默认行为不变），`SseEvent` 增 `form_patch` / `quote_result`，`ToolResult` 增 `events[]`
- `server/quoteProxy.ts`：`/ai` 换成 `createQuoteAiHandler({ geocode, runQuote })`；`runQuote` 复用 `normalizeRequest → callEngine('/route/cost') → buildPublicQuote` **同一条链路**
- 前端：`api.ts` 增 `AiChatHandlers`（`onFormPatch` / `onQuoteResult`）+ 请求体带 `form`；`ChatPanel` 纯增量 props；`QuoteApp` 接 `patch(form)` 与现有结果 state

**实测对话（真引擎 + 真 DeepSeek）**
```
set_route   → 起点 → 南宁；终点 → 河内 Hà Nội
set_cargo   → 已写入：总重 20 吨、货类 normal
run_quote   → 里程约 385.1 公里 · 约 6.1 小时
AI：**初步测算，非正式报价** · 里程约 385.1 公里 · 配车 1 车「低平板 9.6米」·
    参考价区间 **12,800,000 – 15,600,000 VND**
quote_result 含成本词：[]（零泄漏）
```

**验收**：`scripts/verify-quote-ai-range.py` 四段全绿；`quoteTools.test.ts` 12/12；`chatStream.test.ts` 4/4（用 `npx tsx --test`，该文件 import 无 `.ts` 后缀，`node --test` 跑不了）；公开版 `verify-quote-fit.py` 仍 **12/12**、内部版与 5 步表单均 PASS。

**过程中修的五个真 bug**（都不是子代理自报的）
1. `runAgentChat` 硬编码全站助手的工具集 → 开出可注入参数
2. `normalized.value` 是 `{request, notes}`，我误把整个对象喂给引擎（422「引擎暂时不可用」）
3. 引擎对 `length_m/width_m = 0` 直接 422；**无明细时不该造 0 尺寸兜底行**（`normalizeRequest` 本就会补）
4. 执行器读闭包里的初始快照 → 同一轮 `set_cargo` 成功、`run_quote` 却说缺重量。改成可变表单
5. 前端发 `content`、`sanitizeHistory` 只认 `text` → 在 `quoteAi` 里归一

### P4｜✅ 已落地（2026-11-22）内部版配车明细

- 后端 `server/quoteProxy.ts`：`buildInternalFit()` + `/fit` 内部分支，顶层 8 字段（含 `divisibility`）、组内 15 字段逐键显式重建；`isCostKey` 用子串 denylist 断派生键（`fixed_surcharge_vnd` 这类），刻意不匹配裸 `cost` 以保住 `count_doctrine.cost_caliber`
- 前端：`api.ts` 加 `InternalFit` 类型与 `fitVehicles(..., internalKey)` 重载；新 `results/FitDetail.tsx` 渲染四约束分解 / 轴荷线 / 共车组合；`VehicleStep.tsx` 内部版挂载（独立第二个 effect，公开自动配车路径一字未改）

**引擎侧顺带修的 A6 缺陷**：`divisibility` 原本只在 `plan_fleet_by_item` 里算，而 API 层 `len(items) >= 2` 才走它 ⇒ **单件大件永远拿不到拆件建议**（可解体件最常见就是单件）。已在 `plan_fleet()` 补同一段逻辑并透传到 `/reference/fit-vehicles` 顶层。修后 30 m 塔筒 `divisible=true` 得到「拆 2 段 · 每段 15m/12.5t · 三类→一类 · 省内 2 工作日」。引擎 `pytest` 737 passed。

**验收脚本**：`scripts/verify-quote-internal-fit.py`（公开/内部双跑对照 —— 只断言内部版有 `breakdown` 是没判别力的，公开版也给了同样满足；必须同时断言公开版干净）。实测 `INTERNAL-FIT: PASS`。
